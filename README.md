# MyBrain

> 把与 AI 的对话，自动沉淀成一座可检索的个人知识库。

一套跑在 Claude Code 上的个人知识管理系统：**11 个 skill + 1 条全局规则**，让人机协作产生的知识、决策、待办和产出，自动落到 Obsidian 里，并逐层聚合为日报 → 周报 → 月报。

不是笔记模板，是一套**自动归档管道**。

---

## 解决什么问题

和 AI 干活时，真正有价值的东西——踩过的坑、做的架构决策、想明白的方案——都散在一次次对话里。聊完就没了。

手动记？坚持不过三天。全自动记？又会退化成什么都往里塞的流水账。

MyBrain 的答案：**自动捕获要克制，手动归档要全面，两者分开。**

---

## 架构

四层归档 + 一层聚合：

```
                        对话 / 工作过程
                              │
        ┌─────────────────────┼─────────────────────┐
        │                     │                     │
   ┌────▼────┐          ┌─────▼─────┐         ┌─────▼─────┐
   │ Layer 1 │          │  Layer 2  │         │  Layer 4  │
   │ 自动捕获 │          │  手动归档  │         │  外部接入  │
   │ 全局规则 │          │  按类型分流 │         │  飞书消息  │
   └────┬────┘          └─────┬─────┘         └─────┬─────┘
        │                     │                     │
        │  每次会话最多 3 次     │  用户显式触发         │  落到 Inbox
        │                     │                     │
        └─────────────────────┼─────────────────────┘
                              │
                    ┌─────────▼─────────┐
                    │   Obsidian Vault  │
                    │  00_Inbox         │
                    │  01_Daily         │
                    │  02_Reports       │
                    │  03_Knowledge     │
                    │  04_Projects      │
                    └─────────┬─────────┘
                              │
                    ┌─────────▼─────────┐
                    │     Layer 3       │
                    │   聚合与收尾       │
                    │  日报 → 周报 → 月报 │
                    └───────────────────┘
```

| 层 | 触发 | 职责 | 对应 skill |
|---|---|---|---|
| **L1 自动捕获** | 全局规则，自动 | 只捞"非显而易见"的知识点 | `brain-capture` |
| **L2 手动归档** | 用户输入命令 | 深度分析对话，按类型分流 | `save-to-brain` / `save-knowledge` / `save-project` / `process-inbox` |
| **L3 聚合收尾** | 用户输入命令 | 日报 → 周报 → 月报逐层聚合 | `start-my-day` / `end-my-day` / `daily-report` / `weekly-report` / `monthly-report` |
| **L4 外部接入** | 定时 / 手动 | 飞书消息拉进 Inbox | `lark-to-brain` |
| **导航** | 按需 | 定位笔记、理解目录约定 | `obsidian-vault` |

## 快速开始

### 前置

- [Claude Code](https://claude.com/claude-code)（或任何支持 skill 目录的 agent 客户端）
- 一个 [Obsidian](https://obsidian.md) vault

### 安装

```bash
git clone https://github.com/Jivan-sky/My_Brain.git
cd mybrain
./install.sh
```

`install.sh` 会询问你的 vault 路径，把 11 个 skill 装到 `~/.claude/skills/`，全局规则装到 `~/.claude/rules/common/`，并把 skill 里的 `{{VAULT_PATH}}` 占位符替换成你的真实路径。

同时它会**只在文件不存在时**把 `templates/` 下的 `_词表.md` 和 `_资产契约.md` 播种到 vault 根目录——规则文件会去读这两个文件，缺了规则就落不了地。已有版本绝不覆盖。

> 仓库里的 skill 用 `{{VAULT_PATH}}` 占位，是为了不把个人路径硬编码进开源仓库。`install.sh` 在安装时完成替换。

### 用法

装上之后直接对 agent 说人话，或显式调用：

```
/start-my-day          # 早上：整合昨日遗留 + Inbox，生成今日清单
/save-to-brain         # 随时：把当前对话沉淀进知识库
/end-my-day            # 晚上：汇总当天，生成日报
/weekly-report         # 周五：日报聚合为周报
/monthly-report        # 月末：周报聚合为月报
```

## Skill 一览

### 归档

| Skill | 用途 |
|---|---|
| `brain-capture` | **全局规则**（非 skill）：所有项目自动生效，每次会话最多写 3 次 |
| `save-to-brain` | 全量归档：知识 + 决策 + 待办 一次提取分流 |
| `save-knowledge` | 只归档技术知识 → `03_Knowledge/` |
| `save-project` | 只归档项目决策与里程碑 → `04_Projects/` |
| `process-inbox` | 逐条处理 Inbox，决定归档或丢弃 |
| `lark-to-brain` | 拉取飞书消息 → `00_Inbox/`（需要飞书应用凭证） |

### 聚合

| Skill | 用途 |
|---|---|
| `start-my-day` | 生成今日清单 + 晨间简报 |
| `end-my-day` | 汇总当天 → 日报 |
| `daily-report` | 日报生成（含格式规范） |
| `weekly-report` | 日报 → 周报（ISO 周号） |
| `monthly-report` | 周报 → 月报 |

### 导航

| Skill | 用途 |
|---|---|
| `obsidian-vault` | vault 目录约定与笔记定位 |

## 设计决策

这部分是这个项目真正的价值所在。

### 1. 自动捕获必须克制，否则等于没记

L1 是最容易做坏的一层。全自动、无限制地记录，两周后 vault 就变成没人看的流水账。

所以加了**硬性频率上限**：每次会话最多自动写 3 次。

这不是技术限制，是产品设计——**用配额倒逼 AI 做价值判断**。只能写 3 条的时候，它就必须挑最重要的 3 条，而不是把过程全倒出来。

同时明确排除项：简单代码修改、探索性尝试、已经记录过的内容，一律不触发。

### 2. 自动 vs 手动，职责分开

| | L1 自动 | L2 手动 |
|---|---|---|
| 触发 | 系统判断 | 用户命令 |
| 粒度 | 轻、克制 | 深、全面 |
| 上限 | 每次 3 条 | 无 |
| 定位 | 兜底，防止漏记 | 主力，用户主动整理 |

一段对话里 L1 可能只自动捞到 1-2 条，但用户随时可以 `/save-to-brain` 做一次完整梳理。**兜底和主力分离，才不会互相拖累。**

### 3. 追加而非覆盖

同一天可能开多次会话。日报写入用追加，写前先查目标目录是否已有同类内容，有则跳过。

### 4. frontmatter 是硬约束，标签来自受控词表

每条写入必须带 `title` / `created` / `标签`。

`标签` 里的 `type/` **由所在目录决定，且每篇恰好 1 个**：

| tag | 目录 |
|---|---|
| `type/daily` | `01_Daily/YYYY-MM/` |
| `type/weekly` | `02_Reports/周报/YYYY/` |
| `type/monthly` | `02_Reports/月报/YYYY/` |
| `type/knowledge` | `03_Knowledge/` |
| `type/project` | `04_Projects/` |
| `type/moc` | `_MOC.md` / `_词表.md` / `_资产契约.md` |
| `type/meeting` | 会议纪要类 |

取值写死在 vault 根目录的 `_词表.md` 里，**要加新 tag，先加进 `_词表.md` 再使用**。

原因：Obsidian 的 Dataview 查询依赖 frontmatter。**没有 frontmatter 的笔记，在知识库里等于不存在**——它进不了任何视图、任何统计。而 `type/` 唯一且受控，才能用 `sum(type 计数) == md 文件总数` 做完整性校验。

知识卡还多一个硬字段：`source: "[[源笔记]]"`，回链派生它的 L1 记录。

### 5. L1 不可删：提炼 ≠ 搬移

`01_Daily/`（日报）、`02_Reports/`（周报月报）、`04_Projects/`（项目笔记）是**里程记录**——用户的事实表，永久保留。`03_Knowledge/` 只是从它们派生的**视图**。

| 级别 | 目录 | 性质 | 可否移动 |
|---|---|---|---|
| **L1 里程记录** | `01_Daily/`、`02_Reports/` | 事实表（append-only 事件日志） | ❌ 不可移出、不可合并、不可删 |
| **L1 业务实体** | `04_Projects/` | 主表（项目全景/迭代/待办） | ❌ 只可在项目子目录内归位 |
| **L2 派生视图** | `03_Knowledge/` | 从 L1 提炼的意象 | ✅ 可重组、可重切目录 |

推导出的两条硬约束，写进全局规则：

- **从日报抽知识点，原日报留在原地**，知识点新建卡片。
- **严禁在整理/精简/重构方案里提议「删掉已提炼的日记」**。删 Knowledge 卡不损失信息（源还在）；删 L1 记录 = 永久损失。删事实表留视图是本末倒置。

允许的动作：L1 内部归位、补 frontmatter 标签、建 MOC 指向它、从它派生知识卡。

完整规则在 `_资产契约.md`，**任何涉及 L1 的批量操作前先读它**。

### 6. 外部产出必须回流

**任何落在 vault 之外的产出，都要同步一份进知识库**——其他工作目录下的计划书、本地脚本产出的报告、导出文件。

分界线：带项目名/工单号的具体业务 → `04_Projects/<项目>/`；可复用的方法、踩坑、原理 → `03_Knowledge/<主题>/`。

同步后在对应 `_MOC.md` 补链接，并在当日 `01_Daily/` 记一行。

不这么做的话，vault 会退化成"只记了跟 AI 聊天的那部分"，真正的产出反而找不着。

### 7. 聚合是逐层的，不是重新生成

```
日报（事实层）→ 周报（聚合层）→ 月报（聚合层）
```

周报读日报，月报读周报——**月报不需要重新扫一遍原始事实**。

同样重要的是**合并更新而非覆盖**：目标文件已存在时追加，因为用户可能手改过。自动系统最忌讳把人的修改冲掉。

### 8. 待办的跨周期承接

`遗留待办` 是一个贯穿全部报告层的一等公民：

- 日报的遗留 → `start-my-day` 次日承接
- 周报的遗留跨周保留 → 下周一 `start-my-day` 承接
- 月报单列「跨月遗留」节 → 下月承接

checklist 用三态：`- [ ]` 未完成、`- [x]` 本日补完、`~~划线~~` 已废弃。

**废弃和未完成必须区分**——否则清单只增不减，最后就没人看了。

### 9. 路径参数化

所有 skill 里的 vault 路径写成 `{{VAULT_PATH}}`，由 `install.sh` 在安装时替换。

个人路径不进开源仓库，别人也能用自己的目录。

## 目录约定

```
<VAULT_PATH>/
├── _词表.md               — 标签受控词表（新 tag 先加这里）
├── _资产契约.md            — 分级与保留策略（L1 不可删）
├── 00_Inbox/              — 待处理（从外部拉进来的原始条目）
├── 01_Daily/YYYY-MM/      — 日报，按月分层
│   └── YYYY-MM-DD.md
├── 02_Reports/
│   ├── 周报/YYYY/YYYY-WXX.md
│   └── 月报/YYYY/YYYY-MM.md
├── 03_Knowledge/          — L2 派生视图，按主题分类
│   └── <NN-主题>/          — 每个主题子目录一个编号前缀
└── 04_Projects/           — L1 业务实体，按项目分目录
    └── <项目>/
```

顶层数字前缀决定了排序，也决定了 `find` / `grep` 时的可预测性。

`_` 前缀的两个文件是这套系统的**元数据层**：`_词表.md` 划定标签可选范围，`_资产契约.md` 划定哪些目录不许动。两者都带 `type/moc`，和知识卡一样进 Dataview 视图。

## 实战验证

日常是这套流程：早上 `/start-my-day` 起手 → 干活时 L1 自动归档 → 晚上 `/end-my-day` 收尾 → 周五 `/weekly-report` → 月末 `/monthly-report`。
