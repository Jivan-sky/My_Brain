# 一条知识的生命周期

这个文档用一个具体例子，走完一条信息从"对话里冒出来"到"出现在月报里"的全过程。

---

## 场景

你在调试一个部署问题，花了 40 分钟，最后发现是容器网络配置的问题。结论：**容器内访问宿主机服务，要走 `172.18.0.1` 而不是 `127.0.0.1`**。

这个结论值得记。但它是怎么进知识库的？

---

## 第 1 站：L1 自动捕获

对话结束时，全局规则 `brain-capture` 在后台判断：

| 判断项 | 结果 |
|---|---|
| 是"非显而易见"的知识点吗？ | ✅ 是——这是踩坑结论，不是查文档能直接得到的 |
| 是简单代码修改吗？ | ❌ 不是 |
| 已经记录过吗？ | 查 `03_Knowledge/` 下对应主题目录，没有 |
| 本次会话已自动写入几次？ | 0 次，未超 3 次上限 |

四项都过 → 写入。

**写入位置由内容类型决定**，这是规则里写死的映射：

```
技术知识、解决方案      → 03_Knowledge/（按主题分类子目录）
项目进度、完成的任务    → 01_Daily/
重要决策、架构选择      → 04_Projects/（按项目子目录）
周报、月报             → 02_Reports/
```

这条属于"技术知识" → `03_Knowledge/<NN-主题>/2026-09-11-docker容器连宿主机.md`

frontmatter 强制三段：

```yaml
---
title: "容器内访问宿主机服务"
created: 2026-09-11
tags:
  - type/knowledge
  - 部署/docker
source: "[[2026-09-11]]"
---
```

> **为什么 frontmatter 是硬约束？** Obsidian 的 Dataview 靠它建视图。没有 frontmatter 的笔记进不了任何查询——在知识库里等于不存在。
>
> `type/` 由所在目录决定、每篇恰好一个，取值来自 `_词表.md`。`source` 回链派生它的 L1 记录——**知识卡是指针 + 摘要，不是事实本身**。

写入后，agent 只说一句话："已归档到 03_Knowledge/"，不解释细节。

---

## 第 2 站：L2 手动补全（如果需要）

L1 只捞了 1 条。但这次调试过程中你还做了两个项目决策，L1 不会碰（它只捞知识点）。

你可以随时补一刀：

```
/save-to-brain        # 全量：知识 + 决策 + 待办，一次提取分流
/save-project         # 只补项目决策 → 04_Projects/<项目>/
/save-knowledge       # 只补技术知识 → 03_Knowledge/
```

**L1 是兜底，L2 是主力。** 前者怕漏，后者求全。两个上限完全不同（3 条 vs 无限制），互不干扰。

---

## 第 3 站：日报

当天晚上 `/end-my-day`：

1. 读 `01_Daily/YYYY-MM/YYYY-MM-DD.md` 里 L1 已经零散写入的条目
2. 汇总成结构化日报
3. 问你是否要补充
4. 写回同一文件（**已存在则合并，不覆盖**——你可能手改过）

日报是**事实层**。格式固定：

```markdown
## ✅ 完成事项
### 🛠️ <项目A>
- **要点**：说明

## 🧭 关键决策
- **决策** — 理由

## ⏳ 遗留待办
- [ ] **事项**（阻塞原因）
```

checklist 三态：`- [ ]` 未完成 / `- [x]` 本日补完 / `~~划线~~` 已废弃。

**废弃和未完成必须区分**——否则待办清单只增不减，两周后就没人看了。

---

## 第 4 站：跨日承接

第二天早上 `/start-my-day`：

1. 读最近一份日报，抽取**未完成**的遗留待办
2. 扫 `00_Inbox/`，列出待处理条目
3. 查 `04_Projects/` 最近修改的文件，提取项目上下文
4. 去重合并 → 写入今天的日报文件
5. 输出晨间简报

关键动作是**承接**：昨天没做完的，今天自动出现在清单里。不需要你手动搬。

---

## 第 5 站：周报

周五 `/weekly-report`：

- 遍历本周周一到周日的日报
- 按 ISO 周号命名：`02_Reports/周报/YYYY/YYYY-WXX.md`
- 抽取「完成」「关键决策」「遗留」「阻塞」四类
- **合并更新，不覆盖**

周报读日报，不读原始对话。**聚合层不重新扫事实层**，这是分层的意义。

---

## 第 6 站：月报

月末 `/monthly-report`：

- 数据源是**本月周报** + 日报补充
- 写入 `02_Reports/月报/YYYY/YYYY-MM.md`
- 跨月遗留单列一节，供下月 `start-my-day` 承接

链条到这里闭合：

```
对话
 └→ L1 自动捕获 ──┐
                  ├→ 01_Daily（日报）→ 02_Reports/周报 → 02_Reports/月报
    L2 手动归档 ──┤
                  └→ 03_Knowledge（知识，独立沉淀）
                  └→ 04_Projects（决策，独立沉淀）
```

---

## 两条不同的路径

注意上面有**两种知识**，走的是不同的路：

| | 事实/过程 | 知识/决策 |
|---|---|---|
| 例子 | "今天修了线上一个缓存击穿问题" | "容器访问宿主机要走 172.18.0.1" |
| 落点 | 01_Daily → 02_Reports | 03_Knowledge / 04_Projects |
| 生命周期 | 逐层聚合，最终进月报 | 原地沉淀，长期可检索 |
| 会不会被压缩 | 会，月报是浓缩的 | 不会，原样保留 |

**过程会被压缩，知识不会。** 这是设计上的有意区分——月报要短，知识库要全。

---

## Inbox 为什么存在

L4（`lark-to-brain`）从外部拉进来的消息，不直接归档，先进 `00_Inbox/`。

原因：**外部消息的信噪比不可控**。飞书群里 90% 是闲聊，只有 10% 值得留。自动判断容易出错，不如先攒着。

`/process-inbox` 逐条展示，由你决定：归档到知识库 / 归档到项目 / 写入日报 / 丢弃。

**机器负责搬运，人负责判断。**
